1. The RAG system

System S1Does the ingestion pipeline process at least two different document or data types?
ANSWER

Yes, three: Markdown policies, a JSON product catalog, and JSON customer order records.

WHY

src/ingestion/ingest.py splits the three policy files at heading boundaries (45 chunks) and renders the 24 products and 6 fabrics generically from every field (30 chunks). src/context/customers.py loads orders as structured records (not embedded). Rebuilds are incremental by content hash (python -m src.ingestion.build_index, about 8 s from scratch). The synthetic data package (8 customers, 24 SKUs, 3 policies) follows the brief's data section.

System S2Is there an embedding and vector store setup, with written justification?
ANSWER

Yes: bge-small-en-v1.5 run locally through ONNX, stored in FAISS with exact search.

WHY

Justification and the four rejected embedders are in ADR Q2. FAISS replaced Chroma, which would not install on the dev machine. At 15,000 vectors of 384 dimensions the index is about 25 MB and exact search takes a few ms, so approximate search would add only recall risk. Persistence, metadata filtering, model-change detection and incremental sync are about 100 lines in src/ingestion/store.py.

System S3Does retrieval use at least one technique beyond naive top-k?
ANSWER

Yes, four: query routing, hybrid BM25 plus dense search fused by reciprocal rank, exact catalog tools, and an effective-date policy-version filter.

WHY

What each one fixes, and the two that did not earn their keep (rerankers, chunk-question enrichment), is in ADR Q3. Honest note: hybrid vs dense is within noise on this small corpus.

System S4Does generation use a deliberate prompt architecture?
ANSWER

Yes: rules in the system prompt, tagged evidence blocks, question last, and a structured reply with citations and a status.

WHY

Described in ADR Q4 and implemented in src/generation/generate.py. Sonnet 5.5 writes the answer; Haiku 5.5 routes and judges. Policy numbers are never written into the prompt.

System S5Is there a working demo interface?
ANSWER

Yes, a CLI: python -m src.generation.generate "<question>" [--customer CUST-10254].

WHY

It prints the status, answer, citations, flagged data issues, routing and each catalog tool call. Example: python -m src.generation.generate "Can I return the leggings I bought during Cyber Monday?" --customer CUST-10254 answers "No, Final Sale" and cites the order and the policy sections. Customers: CUST-10041 (Maya), CUST-10082 (Jordan), CUST-10103 (Sofia), CUST-10177 (Ethan), CUST-10254 (Priya), CUST-10312 (Lena), CUST-10389 (Marcus), CUST-10421 (Chloe). The brief allows a CLI as the interface.

System S6Is the stack choice justified?
ANSWER

No framework: raw SDK calls plus four small libraries (FAISS, onnxruntime, tokenizers, numpy).

WHY

The corpus is small and each stage has to be inspectable and measurable in a 45-minute debrief. A framework would hide exactly the decisions the brief asks me to defend (chunking, fusion, prompt assembly). The cost is more code of my own: about 3,400 lines across src/ and evals/.

2. Architecture decision record

ADR Q1Chunking strategy: how did you decide chunk size and overlap, and what tradeoffs did you consider?
ANSWER

Policies are split at their own heading boundaries, one chunk per section (15 to 124 words, no overlap). Sections that are always needed together are merged. Products are not chunked for answering; they are served by catalog tools.

WHY
  • Size comes from document structure, not a sweep. Each policy section is one self-contained rule, far below the embedder's 512-token window, and a build-time guard now refuses any chunk that would be silently truncated. Overlap is zero because heading boundaries are the semantic boundaries, and every chunk is prefixed with its document title and heading path so it stands alone.
  • Two merges came from measured failures. The 43-word returns§1 (the 30-day rule) was outscored by longer sibling sections, so I merged it with the eligibility conditions (§1.1); dev recall@5 went 0.80 to 0.93, held-out 0.92 to 0.96. Tier thresholds and tier benefits are always needed together, so they are one chunk, with inherited benefits written out so each tier stands alone.
  • Costs I found: the merged tier chunk is 589 tokens, so I embed a compact 386-token form while the model reads the full text. Writing out inheritance also made the assistant list one-time welcome perks to a long-standing member (H25).
  • Not done: a chunk-size sweep. With 45 policy sections it would measure noise.
ADR Q2Embedding model selection: why this model, and which alternatives did you evaluate and reject?
ANSWER

BAAI/bge-small-en-v1.5 (33M parameters, 384 dimensions), run locally through ONNX.

WHY
  • I compared bge-base, gte-small, all-MiniLM-L6 and e5-small on the dev set. None beat bge-small on the rank-sensitive metrics (hybrid MRR@10: 0.87 vs 0.86, 0.85, 0.85, 0.83). bge-base improved recall@5/10 slightly but lost on R@1 and MRR at about 3x the latency (28 ms vs 8 to 11 ms).
  • The gaps are inside the noise on 30 scored questions, so the tie-break is the cheapest, fastest and simplest option: free, no network, deterministic, and no data leaves the machine.
  • Rejected: hosted embedding APIs (cost, latency, data egress, no measured gain), and bge-large (1.3 GB, slower, no evidence it would help here).
  • Caveat: that comparison ran on an earlier chunking, though the direction was consistent. The index stores the model name and re-embeds fully on a change, because vectors from different models are not comparable.
ADR Q3Retrieval approach: what failure modes does your technique address that naive top-k does not?
ANSWER

The router narrows what is searched. Policies use hybrid search (BM25 plus dense, fused by reciprocal rank) over the policy version in force. Products use exact catalog tools. Customer data is a direct lookup.

WHY

Naive top-k failed in five observable ways, and I address four:

  • Wrong corpus pollutes results: the router has recall 1.0 on every domain across all 61 questions (0 missed domains).
  • List, compare and sort questions ("which leggings have no side seams", "cheapest in the softest fabric") need every match. Catalog tools return the complete filtered set plus total_matches.
  • Superseded policy text: an archived-version filter ensures the model never sees two conflicting rules.
  • Exact terms that embeddings blur ("Final Sale", SKU codes) are why BM25 is in the fusion. Honestly, hybrid vs dense is not distinguishable here (dev MRR 0.90 vs 0.87, held-out 0.83 vs 0.88). I kept it for scale reasons (SKU codes and colour names at 15,000 products), not because it won.
  • Not solved: vocabulary mismatch. "Send back" shares no words with "return", so H24 never retrieves the 30-day rule.
  • Rejected after measuring: two cross-encoder rerankers (MRR 0.75 and 0.80 vs 0.87 for hybrid alone, at 0.7 to 4.8 s per query), fusion-weight tuning (flat), and LLM-generated chunk questions (inconclusive).
ADR Q4Prompt architecture: how is context injected, and how do you handle long or low-relevance retrieved context?
ANSWER

Rules live in the system prompt. Evidence goes in the user message inside tagged blocks (<customer_record>, <source id=…>) that the model is told to treat as data, with the question last. The reply must come back through a structured respond tool: status, answer, citations, data_issues.

WHY
  • The customer record comes from the session, never from the question text, so naming someone else cannot change whose data loads. Code computes durations ("45 days ago"); the policy supplies the window, so a policy change needs no code or prompt edit.
  • Context is capped at 6 excerpts, ordered by rank (about 1,000 tokens). There is no similarity cutoff, because scores cannot separate answerable from unanswerable questions: a product that does not exist scored 0.80 against a 0.71 average for real questions. Instead the model must say what is missing (partial or not_in_data), and a judge verifies that claim.
  • Product questions run a short tool loop (about 1.5 model turns, at most 6). Tool results carry ids and counts so lists cannot be mistaken for complete.
  • Known weaknesses: the model sometimes adds advice no source supports, and this model rejects forced tool choice, so replies are validated and retried.
ADR Q5What would you do differently with two more weeks and a real production dataset?
ANSWER

Fix the vocabulary gap, test at real scale, and replace my hand-built evaluation data with real traffic.

WHY

In priority order:

  1. Scale test. Today every retriever sees 40 to 67% of a 75-chunk corpus, so hybrid and reranking are understated. Generate a 15,000-SKU catalog and a larger policy set and re-run the ablations.
  2. Mine real queries for the "send back" type of mismatch, then fix it with query rewriting or an embedder fine-tuned on (query, chunk) pairs.
  3. A standing support-contact source in every prompt, so a decline or a failed lookup still gives the customer a grounded next step.
  4. A stronger judge. 200+ human labels, plus a check for omitted caveats (my one attempt did not help), run on sampled live traffic.
  5. Lower latency: stream replies, use a faster router, cache the system prompt.
  6. Decide the model on evidence. Haiku as the answerer is 14x cheaper but 10 to 15 points lower on strict pass.

3. The evaluation framework

Eval E1Is there a question set of at least 20 queries across easy, medium and hard difficulty and all three domains?
ANSWER

Yes: 61 questions. 36 dev (evals/questions.jsonl) and 25 held-out (evals/questions_heldout.jsonl).

WHY

22 policy, 19 product, 15 customer or cross-domain, 5 adversarial; 15 easy, 24 medium, 22 hard. Each question maps to named failure modes (evals/failure_modes.md), has gold source ids, a reference answer, and must-include and must-not-include facts. The held-out set was written before further tuning and is the fairer number. Changes made after seeing results are logged in evals/LOG.md: two questions added (L11, H25, marked added: post-hoc in the file), six reference answers edited after the human review (E15), and three gold labels remapped after a chunk merge (E16).

Eval E2Are there at least two retrieval metrics?
ANSWER

Yes: Recall@1/5/10, MRR@10 and NDCG@10, shown beside what a random ranking would score.

WHY

Hybrid retrieval, dev: R@1 0.59, R@5 0.93, R@10 0.97, MRR 0.90, NDCG 0.89 (random: 0.03, 0.13, 0.25, 0.11, 0.13). Held-out: 0.68, 0.96, 0.96, 0.83, 0.86. R@10 looks high but is nearly saturated on a 75-chunk corpus, and R@1 is capped at 0.73 because many questions need several chunks, so MRR and NDCG are the metrics to watch. Product retrieval is scored by "gold sources in context" (0.99 dev, 0.96 held-out), since products use tools.

Eval E3Are there at least two generation metrics?
ANSWER

Yes: faithfulness, hallucination rate, correctness, and a combined strict-pass rate, plus deterministic checks.

WHY

Dev / held-out: faithfulness 0.99 / 1.00, hallucination rate 0.06 / 0.00, correctness 0.97 / 0.94, strict pass 0.89 / 0.92, valid citations 1.00, cross-customer leaks 0. Strict pass moves ±0.03 between identical runs on dev, so read differences under 0.06 as noise. Ten pitfall checks (missing exception, date arithmetic, fabrication, conflated rules, wrong tier, stale data, out-of-scope, privacy, injection, over-refusal) are scored per question.

Eval E4Is there a failure analysis of the three worst examples?
ANSWER

Yes, in evals/FAILURE_ANALYSIS.md: a lookup failure (H24), an overclaim about a latex allergy (A5), and an overgeneralised rule (L9).

WHY

They were chosen by the severity ranking in evals/harness/attribution.py, not by hand. Each is traced through router, retrieval and generation. Across the six questions that did not pass cleanly in the final run: 2 retrieval, 3 generation, 1 eval-side, 0 router.

Eval E5Is there a regression harness that re-runs the evals against a new model or configuration in under five minutes?
ANSWER

Yes: python -m evals.harness.run_all, 167 seconds with no caches.

WHY

It runs preflight, router, retrieval, customer harness, generation, judge-vs-labels, planted-error test, staleness and attribution, compares 42 metrics to evals/baseline.json with tolerances measured from run-to-run noise, and exits non-zero on a regression. --generator, --judge-model and --router-model swap models. I tested it both ways: unchanged passes; swapping the answerer to Haiku fails (strict pass 0.86 to 0.72) and surfaced two bugs in my own checks.

Eval E6Which evaluation tooling did you choose, and why?
ANSWER

A custom claim-level LLM judge plus deterministic checks, not RAGAS, TruLens or DeepEval.

WHY

The judge checks each claim against the exact evidence shown, and scores the ten domain pitfalls the brief's traps imply (Final Sale, window dates, tier perks). That is what the packaged metrics approximate, with less control over the rubric and caching. The judge is Haiku 5.5, about $0.0009 per question. Everything is disk-cached, so a repeat run makes no API calls.

Eval E7Did you evaluate the judge itself?
ANSWER

Yes, three ways: against human labels, with planted errors, and for self-consistency.

WHY
  • Human labels: 12 items labelled by me and 46 by blind labelers (not independent of the model family). Agreement on "any problem": 0.93 (kappa 0.56); on unsupported facts: 1.00.
  • Planted errors: 44 of 50 caught for the right reason (88%); 1 of 53 untouched clean replies and 2 of 16 paraphrases wrongly flagged. It catches added errors almost perfectly and is weak on omissions (0 of 5 dropped exceptions caught); an omission check I tried did not help and was removed. Deterministic Final Sale checks cover that case.
  • Self-consistency: the same 58 answers re-graded three times flip on 4 of 58 items (95.4% pairwise agreement).
Eval E8Is the evaluation cost-efficient?
ANSWER

Yes: a full uncached run costs about $1.50 (estimated from the measured per-call costs) and every call is cached.

WHY

The judge is the cheapest capable model, calls run concurrently, and cached results include the original latency and tokens so repeat runs are free. The noise study (three uncached repeats) cost a few dollars once; its outputs are saved.

4. Reliability and production readiness

Memo Q1Staleness and index drift: how do you handle policy updates or catalog changes without a full re-index?
ANSWER

Chunks are keyed by a hash of their content, so an update re-embeds only what changed; a drift check detects an index that no longer matches its source; catalog facts are read live; and policies are versioned by effective date.

WHY

Tested in evals/staleness_eval.py (24 of 24 checks) on a scratch copy:

  • A simulated update across two policies and the catalog re-embedded exactly 4 of 75 chunks. Answers followed at once: an order 45 days old flipped from "outside the window" to "returnable through March 16"; an unrelated answer did not change.
  • python -m src.ingestion.build_index --check lists stale chunks and exits non-zero. Building it exposed a real bug: metadata changes were invisible to a text-only hash, and the "current policy" filter silently returned nothing. Metadata is now hashed separately.
  • The policy version in force keeps stable ids; others are archived and not embedded. A version switch re-embedded only the 2 chunks whose text differed.
  • Open: one rule spelled in several sections must be edited consistently ("30 days" appears in two different rules); an embedder upgrade needs a full re-embed (detected); version flips need a scheduled job.
Memo Q2Retrieval failure modes: what happens when nothing relevant is retrieved, and how do you detect and handle it?
ANSWER

Out-of-scope questions are declined before retrieval. Otherwise retrieval always returns its top 6, so the safeguard is the model's structured status (partial or not_in_data), verified by a judge and a citation check, with human escalation as the planned fallback.

WHY
  • A similarity threshold does not work: a nonexistent product scored 0.80 against a 0.71 average for real questions, and reranker scores overlap too.
  • For questions outside the data it works: all three refuse/abstain questions were handled, and the false-refusal rate is 3 to 4%.
  • It fails safely but unhelpfully when the section exists and was not found. For H24 ("send back the leggings from my first order") the 30-day rule ranked 11th to 20th, so the reply said it could not confirm, when the answer is "no, 138 days". This is the largest quality gap.
  • To close it: always include the few core rules every return question needs, retry once with a rewritten query on not_in_data, and give a grounded support contact (designed, not built).
Memo Q3Latency budget: what are your estimated p50 and p95 latencies, where are the bottlenecks, and how would you optimise?
ANSWER

Measured uncached over 61 questions: p50 5.5 s and p95 9.1 s end to end. The answer model is about 84% of that, the router about 16%, and retrieval is negligible.

WHY
  • p50 / p95 by stage: router 0.85 / 1.2 s; retrieval 8 to 22 / 15 to 60 ms; answer model 3.9 to 4.6 / 6.6 to 8.8 s (1.4 to 1.5 turns, since product questions call tools). The judge (about 4 s) is evaluation only.
  • Cost: $0.015 per question to answer, $0.0009 to judge; a full uncached eval run is about $1.50.
  • Levers, biggest first: stream the reply; a smaller or rule-based router; cache the system prompt; cap tool turns. A cheaper answer model is not free: Haiku 5.5 was 14x cheaper but 10 to 15 points lower on strict pass.
Memo Q4Guardrails and out-of-scope queries: how do you prevent the system from confidently answering what it should not?
ANSWER

Layers: the router sends out-of-scope questions to a fixed decline with no model call; customer data loads only for the signed-in session; the prompt forbids guessing, other customers' data and policy exceptions; every reply is checked for valid citations and for other customers' identifiers.

WHY
  • Results: 0 cross-customer leaks and 100% valid citations in 61 questions; the competitor, other-customer, nonexistent-product and "my manager approved it" cases all behaved correctly. Asking about "Jordan Kim" in Maya's session loads only Maya's record.
  • The harness caught a cheaper answer model by its strict-pass drop, and exposed a false positive in my own leak check (a refusal repeating the name the user typed), now fixed. Model choice is gated by the harness, not by price.
  • Gaps: only 5 adversarial questions; instructions hidden in data fields (an order note, a product description) are untested; the judge is an offline measure, not a runtime guard. Next step: run the cheap deterministic checks on every live reply.
Memo Q5Observability: what would you instrument and monitor in production?
ANSWER

A trace per request, a few rate metrics with alert thresholds taken from the measured noise, a sampled quality score, and an index-freshness gauge.

WHY
  • Per request: router decision and latency; retrieved ids and scores; each tool call with its arguments, result count and errors; turns, tokens and cost; reply status; citation validity; the policy and index version that answered.
  • Rates: answered / partial / not_in_data / declined shares (a rising not_in_data means a retrieval or content gap), false refusals, tool errors, escalations.
  • Quality: judge about 5% of replies. Alert on a drop larger than twice the run-to-run spread measured here (about 0.06 on strict pass), not on any dip. Run build_index --check on a schedule and alert on drift. Review the top not_in_data queries weekly.

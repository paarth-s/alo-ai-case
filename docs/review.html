1. The RAG system

System S1Does the ingestion pipeline process at least two different document or data types?
ANSWER

Yes, three: Markdown policies, a JSON product catalog, and JSON customer order records.

WHY

src/ingestion/ingest.py splits the three policy files at heading boundaries (45 chunks, embedded). The product catalog (24 products, 6 fabrics) and the customer orders are structured JSON, so they are loaded as typed records and queried with exact tools (src/context/catalog.py, customers.py), not embedded. Rebuilds are incremental by content hash (python -m src.ingestion.build_index, about 8 s from scratch). The data is the synthetic package supplied with the case (8 customers, 24 SKUs, 3 policies). The brief suggests 20 to 50 customers; I used the supplied 8 and wrote the 61 questions myself.

System S2Is there an embedding and vector store setup, with written justification?
ANSWER

Yes: bge-small-en-v1.5 run locally through ONNX, stored in FAISS (exact search).

WHY

Justification and the four rejected embedders (code removed, numbers in evals/LOG.md E9) are in ADR Q2. Exact FAISS search has no recall loss to explain; persistence, metadata filtering and incremental sync (re-embed only changed chunks) are our code in src/ingestion/store.py. I also built the store on Chroma and re-ran every eval: identical retrieval metrics on every metric at the time, no code saved, and an install of 11 to 12 minutes against 24 seconds, so FAISS stays. Production would use pgvector behind the same VectorStore interface.

System S3Does retrieval use at least one technique beyond naive top-k?
ANSWER

Yes, four: query routing, hybrid BM25 plus dense search fused by reciprocal rank, exact catalog tools, and an effective-date policy-version filter.

WHY

What each one fixes, and the two that were tried and rejected (cross-encoder rerankers, LLM-written chunk questions; code removed, numbers kept in evals/LOG.md), is in ADR Q3. Honest note: hybrid vs dense is within noise on this small corpus.

System S4Does generation use a deliberate prompt architecture?
ANSWER

Yes: rules in the system prompt, tagged evidence blocks, question last, and a structured reply with citations and a status.

WHY

Described in ADR Q4 and implemented in src/generation/generate.py. Sonnet 5.5 writes the answer; Haiku 5.5 routes and judges. Policy numbers are never written into the prompt.

System S5Is there a working demo interface?
ANSWER

Yes, two: a CLI, python -m src.generation.generate "<question>" [--customer CUST-10254], and a small local web page, python -m src.web.app (http://127.0.0.1:8000, interface only), whose /design page shows each design choice, why it was chosen, and the live baseline metrics.

WHY

It prints the status, answer, citations, flagged data issues, routing and each catalog tool call. Example: python -m src.generation.generate "Can I return the leggings I bought during Cyber Monday?" --customer CUST-10254 answers "No, Final Sale" and cites the order and the policy sections. Customers: CUST-10041 (Maya), CUST-10082 (Jordan), CUST-10103 (Sofia), CUST-10177 (Ethan), CUST-10254 (Priya), CUST-10312 (Lena), CUST-10389 (Marcus), CUST-10421 (Chloe). The brief allows a CLI as the interface.

System S6Is the stack choice justified?
ANSWER

No framework: raw SDK calls plus four small libraries (FAISS, onnxruntime, tokenizers, numpy).

WHY

The corpus is small and each stage has to be inspectable and measurable in a 45-minute debrief. A framework would hide exactly the decisions the brief asks me to defend (chunking, fusion, prompt assembly). The cost is more code of my own: about 3,200 lines across src/ and evals/.

2. Architecture decision record

ADR Q1Chunking strategy: how did you decide chunk size and overlap, and what tradeoffs did you consider?
ANSWER

Policies are split at their own heading boundaries, one chunk per section (15 to 124 words, no overlap). A few sections that are always needed together are merged. For example, information about loyalty and the details of each tier's perks, which were different sections but were nearly always used together. Products are not chunked for answering; they are served by catalog tools.

WHY
  • Size follows document structure, not a sweep. Each section is one self-contained rule, far below the embedder's 512-token window, and a build-time guard refuses any chunk that would be truncated. Overlap is zero because headings are the semantic boundaries; each chunk is prefixed with its title and heading path so it stands alone.
  • Two merges came from measured failures. The 43-word 30-day rule (returns§1) was outscored by longer sibling sections, so I merged it with the eligibility conditions: dev recall@5 went 0.80 to 0.93, held-out 0.92 to 0.96 (on the earlier all-domain metric). Tier thresholds and benefits are one chunk, with inherited benefits written out so each tier stands alone.
  • Costs: the merged tier chunk is 589 tokens, so I embed a 386-token form while the model reads the full text. Writing out inheritance also made the assistant list one-time welcome perks to a long-standing member (H25).
  • Not done: a chunk-size sweep. With 45 sections it would measure noise.
ADR Q2Embedding model selection: why this model, and which alternatives did you evaluate and reject?
ANSWER

BAAI/bge-small-en-v1.5 (33M parameters, 384 dimensions), run locally through ONNX.

WHY
  • I compared bge-base, gte-small, all-MiniLM-L6 and e5-small on the dev set. None beat bge-small on the rank-sensitive metrics (hybrid MRR@10: 0.87 vs 0.86, 0.85, 0.85, 0.83). bge-base improved recall@5/10 slightly but lost on R@1 and MRR at about 3x the latency (28 ms vs 8 to 11 ms).
  • The gaps are inside the noise on 30 scored questions, so the tie-break is the cheapest, fastest and simplest option: free, no network, deterministic, and no data leaves the machine.
  • Rejected: hosted embedding APIs (cost, latency, data egress, no measured gain) and bge-large (1.3 GB, no evidence it helps here).
  • Caveat: that comparison ran on an earlier chunking, though the direction was consistent. The index stores the model name and re-embeds fully on a change.
ADR Q3Retrieval approach: what failure modes does your technique address that naive top-k does not?
ANSWER

The router narrows what is searched. Policies use hybrid search (BM25 plus dense, fused by reciprocal rank) over the policy version in force. Products use exact catalog tools. Customer data is a direct lookup.

WHY

Naive top-k failed in five observable ways, and I address four:

  • Wrong corpus pollutes results: the router has recall 1.0 on every domain across all 61 questions.
  • List, compare and sort questions ("which leggings have no side seams") need every match. Catalog tools return the full filtered set plus total_matches.
  • Superseded policy text: an archived-version filter ensures the model never sees two conflicting rules.
  • Exact terms that embeddings blur ("Final Sale") are why BM25 is in the fusion. Honestly, the evidence does not support it yet: on policy text, hybrid beats dense on dev (MRR 0.87 vs 0.83) and loses on held-out (0.74 vs 0.88), over only 21 and 16 scored questions. I kept hybrid as the textbook guard for exact terms; dense alone is the simpler candidate and the first thing I would re-test at scale.
  • Not solved: vocabulary mismatch. "Send back" shares no words with "return", so H24 never retrieves the 30-day rule.
  • Rejected after measuring: two cross-encoder rerankers (MRR 0.75 and 0.80 vs 0.87 for hybrid alone, at 0.7 to 4.8 s per query), fusion-weight tuning (flat), and LLM-generated chunk questions (inconclusive).
ADR Q4Prompt architecture: how is context injected, and how do you handle long or low-relevance retrieved context?
ANSWER

Rules live in the system prompt. Evidence goes in the user message inside tagged blocks (<customer_record>, <source id=…>) that the model treats as data, with the question last. The reply must come back through a structured respond tool: status, answer, citations, data_issues.

WHY
  • The customer record comes from the session, never from the question text, so naming someone else cannot change whose data loads. Code computes durations ("45 days ago"); the policy supplies the window, so a policy change needs no code or prompt edit.
  • Context is capped at 6 excerpts in rank order (about 1,000 tokens). There is no similarity cutoff, because scores cannot separate answerable from unanswerable questions (a nonexistent product scored 0.80 against 0.71 for real ones). Instead the model must say what is missing (partial or not_in_data), and a judge verifies that claim.
  • Product questions run a short tool loop (about 1.5 model turns, at most 6). Results carry ids and counts so lists cannot be mistaken for complete.
  • Known weaknesses: the model sometimes adds advice no source supports, and it rejects forced tool choice, so replies are validated and retried.
ADR Q5What would you do differently with two more weeks and a real production dataset?
ANSWER

Fix the vocabulary gap, test at real scale, and replace my hand-built evaluation data with real traffic.

WHY

In priority order:

  1. Scale test. Today every retriever scans only 45 policy chunks (the top 10 is 22% of everything), so hybrid and reranking are understated. Generate a 15,000-SKU catalog and a larger policy set and re-run the ablations. Grow the customer set too (8 supplied; the brief suggests 20 to 50).
  2. Mine real queries for "send back" type mismatches, then fix with query rewriting or an embedder fine-tuned on (query, chunk) pairs.
  3. A standing support-contact source in every prompt, so a decline still gives a grounded next step.
  4. A stronger judge: 200+ human labels and a check for omitted caveats (my one attempt did not help), run on sampled live traffic.
  5. Lower latency: stream replies, a faster router, a cached system prompt.
  6. Decide the model on evidence. Haiku as the answerer is 14x cheaper but 10 to 15 points lower on strict pass.

3. The evaluation framework

Eval E1Is there a question set of at least 20 queries across easy, medium and hard difficulty and all three domains?
ANSWER

Yes: 61 questions. 36 dev (evals/questions_dev.jsonl) and 25 held-out (evals/questions_heldout.jsonl).

WHY

22 policy, 19 product, 15 customer or cross-domain, 5 adversarial; 15 easy, 24 medium, 22 hard. Each question maps to named failure modes (evals/failure_modes.md), has gold source ids, a reference answer, and must-include and must-not-include facts. The held-out set was written before further tuning and is the fairer number. Changes made after seeing results are logged in evals/LOG.md: two questions added (L11, H25, marked added: post-hoc in the file), six reference answers edited after the human review (E15), and three gold labels remapped after a chunk merge (E16).

Eval E2Are there at least two retrieval metrics?
ANSWER

Yes: Recall@1/5/10, MRR@10 and NDCG@10, shown beside what a random ranking would score.

WHY

Retrieval is scored on policy questions only, because policy text is the only thing searched (21 dev and 16 held-out questions have policy gold). Hybrid, dev: R@1 0.58, R@5 0.94, R@10 0.98, MRR 0.87, NDCG 0.87 (random: 0.02, 0.11, 0.22, 0.09, 0.11). Held-out: 0.53, 0.94, 0.94, 0.74, 0.79. R@10 is nearly saturated on a 45-chunk corpus, and R@1 is capped at 0.77 (dev) because many questions need several chunks, so MRR and NDCG are the metrics to watch. Dense alone scores MRR 0.83 dev and 0.88 held-out, so hybrid is not clearly better. Products use tools and are scored by "gold sources in context" (0.99 dev, 0.96 held-out). An earlier version also scored product questions against an embedded product index that answering never used; that inflated MRR (0.90 dev, 0.83 held-out), and I removed it.

Eval E3Are there at least two generation metrics?
ANSWER

Yes: faithfulness, hallucination rate, correctness, and a combined strict-pass rate, plus deterministic checks.

WHY

Dev / held-out: faithfulness 1.00 / 1.00, hallucination rate 0.06 / 0.00, correctness 0.99 / 0.94, strict pass 0.86 / 0.92, valid citations 1.00, cross-customer leaks 0. Strict pass moves ±0.03 between identical runs on dev, so read differences under 0.06 as noise; on the 25 held-out questions one question is 0.04, so a swing of two is still noise (H15 is a borderline judge call, see the failure analysis). Ten pitfall checks (missing exception, date arithmetic, fabrication, conflated rules, wrong tier, stale data, out-of-scope, privacy, injection, over-refusal) are scored per question.

Eval E4Is there a failure analysis of the three worst examples?
ANSWER

Yes, in evals/FAILURE_ANALYSIS.md: a retrieval miss (H24, "send back" vs "return"), over-hedging on a self-contradicting policy (H15), and a mislabelled status on a latex-allergy question (A5), each with the assistant's actual reply quoted.

WHY

They are the three questions that failed strict pass in all four uncached runs (the other six failures are intermittent and listed in a table). Each is traced through router, retrieval and generation. Across the seven questions that did not pass in the committed run: 2 retrieval, 5 generation, 0 router.

Eval E5Is there a regression harness that re-runs the evals against a new model or configuration in under five minutes?
ANSWER

Yes: python -m evals.harness.run_all, 167 seconds with no caches.

WHY

It runs preflight, router, retrieval, customer harness, generation, judge-vs-labels, planted-error test, staleness and attribution, compares 42 metrics to evals/baseline.json with tolerances measured from run-to-run noise, and exits non-zero on a regression. --generator, --judge-model and --router-model swap models. I tested it both ways: unchanged passes; swapping the answerer to Haiku fails (strict pass 0.86 to 0.72) and surfaced two bugs in my own checks.

Eval E6Which evaluation tooling did you choose, and why?
ANSWER

A custom claim-level LLM judge plus deterministic checks, not RAGAS, TruLens or DeepEval.

WHY

The judge checks each claim against the exact evidence shown, and scores the ten domain pitfalls the brief's traps imply (Final Sale, window dates, tier perks). That is what the packaged metrics approximate, with less control over the rubric and caching. The judge is Haiku 5.5, about $0.0009 per question. Everything is disk-cached, so a repeat run makes no API calls.

Eval E7Did you evaluate the judge itself?
ANSWER

Yes, three ways: against human labels, with planted errors, and for self-consistency.

WHY
  • Human labels: 12 items labelled by me and 46 by blind labelers (not independent of the model family). Agreement on "any problem": 0.86 in the latest run and 0.93 in the one before (4 of 58 items flip between repeats); on unsupported facts: 1.00.
  • Planted errors: 44 to 47 of 50 caught for the right reason (88 to 94% across three runs); 1 to 3 of 53 untouched clean replies and 1 to 2 of 16 paraphrases wrongly flagged. It catches added errors almost perfectly and is weak on omissions (0 to 2 of 5 dropped exceptions caught); an omission check I tried did not help and was removed. Deterministic Final Sale checks cover that case.
  • Self-consistency: the same 58 answers re-graded three times flip on 4 of 58 items (95.4% pairwise agreement).
Eval E8Is the evaluation cost-efficient?
ANSWER

Yes: a full uncached run costs about $1.50 (estimated from the measured per-call costs) and every call is cached.

WHY

The judge is the cheapest capable model, calls run concurrently, and cached results include the original latency and tokens so repeat runs are free. The noise study (three uncached repeats) cost a few dollars once; its outputs are saved.
